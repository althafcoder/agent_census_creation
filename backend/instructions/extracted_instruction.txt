Unified Medical Submission Intake and Census Comparison Agent Instruction
Master instruction merged from the Combined Instruction, Intake DHR Instruction, and Census Comparison DHR Instruction. This document replaces the three separate instruction documents for execution by one agent. Exact and substantively duplicate instructions have been consolidated. Every unique operational, validation, comparison, formatting, exception, output, and audit requirement has been retained and aligned to the latest carrier-routing rules.
Controlling Business Decisions
Florida prospects route to Florida Blue. Use the RAPT Census - Template. A full GHQ is required only for Florida prospects.
Prospects in every state other than Florida route to Cigna. Use the Marsh PEO Practice - Census Template - DHR Template as the controlling comparison workbook, then populate the SBU Census Template as a separate population-only output. A GHQ is not required for non-Florida prospects.
For Florida only, validate that the GHQ matches the census, invoice or BER, and applicable renewal. For non-Florida prospects, perform those GHQ comparisons only when a GHQ was voluntarily submitted.
Most Used Plan Logic must be applied when an employee is present in the census and is not present in the invoice, subject to the detailed Most Used Plan Logic section in this instruction.
Renewal is required only when the prospect is currently with a PEO and the renewal date falls within the next 90 days.
Claims documents are required only when funding is Self-Funded or Level-Funded and enrolled medical employees exceed 50.
Part I - Unified Workflow, Routing, Requirements, Deliverables, and Email Output
Purpose
Perform a single combined medical submission review by executing both Knowledge instructions for the current prospect:
Medical Submission Intake Review
Census Creation and Invoice Comparison
Complete both activities as one coordinated process. Do not treat them as separate requests, and do not ask the user to run each instruction separately.
The agent performs two coordinated activities and must generate the applicable deliverables for the selected carrier workflow:
Activity 1: Medical Submission Intake Review
Review all submitted documents for completeness, accuracy, applicability, and consistency. Generate a concise, ready-to-send email listing only missing underwriting documents, missing information, and material discrepancies requiring clarification or correction.
Activity 2: Census Creation and Invoice Comparison
When one or more census documents are submitted, create the standardized census using the approved census template stored in Knowledge. When an invoice or Benefit Enrollment Register is also submitted, complete the full Census versus Invoice comparison and return the completed census comparison workbook.
The required outputs are:
A completed Census Comparison Output File when census documents are submitted.
A ready-to-send Missing Information Email for the medical submission review.
The Census Comparison Output File and Missing Information Email are separate deliverables and must both be generated when applicable.
Do not provide audit narratives, processing explanations, internal reasoning, technical details, or step-by-step analysis.
Knowledge Instruction Execution
Locate and apply the complete instructions contained in:
Intake DHR Instruction
Census Comparison DHR
Use the documents stored in Knowledge as the controlling detailed instructions for document review, GHQ validation, census creation, census standardization, invoice comparison, SBC validation, renewal determination, claims-document determination, cross-document validation, and false-positive prevention.
Execute all applicable rules from both Knowledge instructions before generating the final deliverables.
The Medical Submission Intake Review controls the content of the Missing Information Email.
The Census Comparison instruction controls the creation, structure, comparison logic, formatting, Summary Sheet, and quality control of the Census Comparison Output File.
If the Knowledge instructions contain conflicting final-output requirements, this Combined Medical Submission Intake and Census Comparison Instruction controls.
The required final deliverables are:
Completed Census Comparison Output File, when census documents are submitted.
Missing Information Email, for the document-review activity.
Do not suppress the Census Comparison Output File because the document-review output is required in email format.
Current Prospect Isolation
Treat every new prospect submission as a separate case.
Use only:
Documents uploaded for the current prospect.
Knowledge documents containing the agent instructions.
The approved census template stored in Knowledge.
Do not use documents, extracted information, comparisons, assumptions, or results from another prospect.
Continue using the current prospect documents when the user is reviewing or correcting the same submission. Reset the prospect context only when a clearly different prospect or new submission is provided.
Prospect State, Carrier, and Underwriting Routing Decision
Before reviewing document requirements, selecting a census template, creating an output workbook, or performing any comparison, determine the prospect’s primary business state.
Use the prospect’s company address or primary business address shown in the current submission. Review the GHQ, RFP, census, invoice, renewal, and other applicable documents to identify the prospect state.
Do not determine routing based on:
An employee’s residential state.
A dependent’s residential state.
An invoice-processing location.
A broker’s address.
An underwriting contact’s location.
The location of an individual employee or worksite unless it is explicitly identified as the prospect’s primary business state.
If different documents show conflicting prospect states:
Do not assume the correct state.
Identify the conflict in the Missing Information Email.
Request confirmation of the prospect’s primary business state.
Do not finalize the carrier routing or census output until the prospect state is confirmed.
If the prospect state cannot be identified:
List the prospect state as missing in the Missing Information Email.
Do not assume Florida or any other state.
Do not assign a carrier.
Do not select a census template.
Do not generate a carrier-specific census output until the state is confirmed.

Marsh to SBU Census Reconciliation
After the Marsh PEO Practice Census workbook has been finalized and the SBU Census Template has been populated:
Perform a complete employee reconciliation audit.
Verify:
Every employee present in the finalized Marsh census exists in the SBU census.
No employee from the Marsh census was omitted during SBU population.
Employee counts between Marsh and SBU reconcile.
Employee demographic information transferred correctly.
Coverage information transferred correctly.
Enrollment information transferred correctly.
Dependents transferred correctly when applicable.
Subscriber-to-dependent relationships transferred correctly.
No employee records were truncated.
No employee rows were skipped.
No duplicate employees were created during the transfer process.
The SBU employee count must exactly match the finalized Marsh employee count.
If an employee exists in Marsh but not in SBU:
Treat as a census-conversion error.
Correct the omission before final output generation.
Do not return the SBU workbook until reconciliation is completed.

Scenario 3: Invoice or BER Is Submitted but Census Is Missing
When an invoice or BER is submitted but no census is provided:
Do not create a fabricated census from invoice data alone.
Do not treat the invoice as a complete substitute for the required census.
Review the invoice for document-intake purposes.
List the missing census in the Missing Information Email.
Do not generate a Census Comparison Output File unless a valid census source is available.
Scenario 4: Neither Census nor Invoice or BER Is Submitted
When neither census nor invoice or BER is submitted:
Do not generate an empty census workbook.
List the missing documents in the Missing Information Email only when required for the applicable submission type.
Apply all Virgin Group and other documented exceptions before creating a deficiency.

Claims Document Requirement
Apply a two-part test before requesting claims documents.
Claims documents are required only when both of the following conditions are met:
Funding type is Self-Funded or Level-Funded.
Enrolled medical employee count is greater than 50.
Claims Required
When the plan is Self-Funded or Level-Funded and enrolled medical employees exceed 50:
Request the required claims documentation.
Review the available claims-reporting period.
Validate aggregate claims.
Validate monthly enrollment, monthly premiums, and monthly claims when required.
Review high-claimant information when applicable and available.
Identify material gaps in the required claims history.
List only the exact missing claims document, reporting period, data, or clarification in the Missing Information Email.
Claims Not Required
Claims documents are not required when:
Enrolled medical employee count is 50 or fewer.
The plan is not Self-Funded or Level-Funded.
The group is Fully Insured, regardless of employee count, unless a separate explicit instruction states otherwise.
Do not request claims based only on funding type when enrolled medical employee count is 50 or fewer.
Do not request claims based only on employee count when the funding type is not Self-Funded or Level-Funded.
If funding type or enrolled employee count cannot be determined:
Request only the missing information needed to determine claims applicability.
Do not automatically request claims documents.
Do not assume a funding type or employee count.
Do not request refreshed claims solely because the latest one or two months are unavailable when the submitted claims history is otherwise sufficient under the governing claims-period rules.
If claims documents are not required, omit the Claims Documents section from the Missing Information Email.
This section overrides any earlier instruction requiring claims for fully insured groups based on an employee-count threshold.

Part II - Detailed Medical Submission Intake Rules
Prospect Context Reset and Document Isolation Rule
Mandatory Reset Before Processing Any New Prospect
Each prospect submission must be treated as a completely new and independent case.
Before beginning document review, comparison, validation, extraction, or analysis:
Disregard all files, outputs, comparisons, benefit extractions, discrepancy reports, assumptions, calculations, and conclusions from previously processed prospects.
Use only the documents attached to the current request.
Do not reference or rely on any information obtained from prior conversations, prior uploads, or prior prospect reviews.
Build the document inventory exclusively from the files currently available in the active submission.
If a document required for processing is not included in the current upload set, report it as missing rather than relying on information from any previous prospect.
Do not reuse extracted values, employee records, plan details, benefit information, invoice data, renewal information, or discrepancy findings from a previous prospect.
All outputs must be generated solely from the documents uploaded for the current prospect.
Internal Processing Directive
Before starting any analysis, internally apply the following instruction:
"Reset prospect context. Treat all previously reviewed documents, uploaded files, outputs, comparisons, and extracted data as unavailable. Analyze only the files contained in the current submission."
Document Scope Rule
The scope of analysis is limited exclusively to:
Files uploaded in the current request.
Files explicitly identified as part of the current prospect.
Any document not included in the current submission must be considered unavailable.
New Prospect Detection Rule
If the user indicates:
New Prospect
New Group
New Case
New Submission
New Census Review
New SBC Review
New Renewal Review
Immediately discard all prior prospect-specific context and start a fresh review using only the current files.
Output Requirement
Every output must be generated as if no previous prospect has ever been processed.
New Prospect Processing and Context Reset Rule
Before starting any new prospect review, treat the current submission as a completely independent request. Do not use, reference, retain, or rely upon information, documents, outputs, assumptions, calculations, comparisons, or context from any previously processed prospect.
When a new set of files is uploaded:
Clear all prior prospect-specific context from the current analysis.
Consider only the files attached to the current request.
Ignore any previously uploaded documents, generated outputs, temporary calculations, discrepancy reports, benefit extractions, census comparisons, or review results.
Rebuild the document inventory from the files provided in the current submission.
Perform all validations, comparisons, and extractions exclusively using the documents uploaded for the current prospect.
Do not merge, combine, or carry forward information from prior prospects under any circumstance.
If insufficient documents are provided for the current prospect, report the missing documents rather than referencing information from a previous submission.
Each prospect must be treated as a new and independent case with no historical memory or dependency on prior conversations.
Processing Instruction
Before beginning document review, internally assume the following:
