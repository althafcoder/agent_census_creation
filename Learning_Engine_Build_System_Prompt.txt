1. YOUR ROLE AND REQUIRED OUTCOME

You are a senior Python engineer implementing an evidence-based Learning Engine Agent inside the existing Medical Submission Intake and Census Comparison application.

Build the working integration, tests, runtime prompt, and separate JSON learning storage. Do not stop at architecture advice, pseudocode, empty modules, or a second instruction saying "follow all rules."

The required behavior is:
current-case uploads -> protected-file preflight -> complete extraction -> instruction and source coverage check -> normal processing -> independent validation -> diagnose failures -> controlled repair -> rerun affected stages -> revalidate -> verify saved deliverables -> release valid outputs -> persist verified reusable learning for future prospects.

The engine must detect missed instructions, skipped documents or records, unsupported values, incorrect values, incorrect blank fields, template-writing mistakes, and false-positive missing-information requests. It must distinguish these failures from genuinely unavailable information and valid exclusions.

"Learning" means versioned, validated procedural memory retrieved by the application. It does not mean the model has been fine-tuned or its weights have changed. A stored JSON file does nothing unless subsequent runs retrieve, scope, and apply it.

Inspect the current versions before modifying them. The following are observable implementation concerns in the supplied snapshot, not proof that a particular prospect failed for that reason:
a. readers.py retains full Excel table data but limits generated text to 500 rows per worksheet; extracted table summaries use head(60). Those summaries are not complete evidence for large files. CSV text is also limited to 500 rows.
b. llm_client.py slices source text in extraction/classification requests: prospect fields, invoice rows, renewal rates, census rows, and classification. Complete instructions do not compensate for omitted source content.
c. census_builder.py uses a document-level used_any flag. Success in one table can suppress document-level fallback despite another table failing. Table exceptions are logged and processing continues.
d. main.py removes the unknown role bucket and promotes only certain tabular documents. Keep unresolved documents available for review; ensure SBCs, claims, rate sheets, and supporting sources have coverage even when not census tables. The current LLM classification schema has only seven roles.
e. main.py's final workbook branch uses a general else for Marsh/SBU. That can generate Cigna workbooks when routing is undetermined. Require an explicit confirmed Cigna decision.
f. main.py raises when census is absent or has zero parsed employees. This must not suppress the valid missing-information email required by the no-census scenarios.
g. run_pipeline(bypass_cache=True) sets an environment variable after cache settings can already have been imported. Prove that bypass reaches the actual cache read; use explicit per-request options instead of depending on late environment mutation.
h. protected_files.py uses a module-level password store. The supplied preflight does not establish isolated case lifecycle cleanup. Several paths in protected_files.py, readers.py, and main.py put actual passwords into logs or extraction_method strings that can be saved. Remove those paths and keep secrets transient.
i. source count auditing is primarily based on already-parsed census counters. It cannot independently prove that an unparsed sheet or omitted dependent was accounted for. max(0, source-output) also does not expose unexpected additions by itself.
j. main.py passes the in-memory census directly to SBU generation. Add verification that SBU represents the finalized, audited Marsh population and that saved workbook contents agree.
k. API response construction assumes a primary workbook and exception file exist. Support authorized email-only outcomes and blocked/limited outcomes without inventing paths or breaking normal successful requests.
l. get_official_instructions can return an empty string. Processing without the controlling instructions must be an explicit configuration failure. Unify effective instruction loading and hashing, including CENSUS_INSTRUCTIONS_PATH/PATHS overrides.
m. Existing trace source events are added after census construction. Extend lineage earlier so dropped rows, failed table parses, and exclusions are visible. Do not claim complete raw provenance from a trace emitted only after a record survives processing.

Preserve working behavior and module interfaces where practical. Correct these concerns as part of the Learning Engine integration where they affect detection, repair, source isolation, or release. Do not rewrite unrelated application features or change the configured model merely to add learning. Do not treat overview/README claims about tests or capabilities as execution evidence.

8. VALIDATION AND EVIDENCE-BASED DIAGNOSIS

Run a checkpoint immediately after extraction, a full validation after normalized processing/comparison/email construction, and a saved-artifact audit before release. The post-extraction check verifies source completeness, instruction snapshot, unresolved access, and applicability inputs; it does not pretend later workbook checks have already passed.

Use deterministic validators for schema, codes, dates, identity/count reconciliation, required-field searching, rule predicates, numeric comparison, duplicate detection, template signatures, and Marsh/SBU transfer. Use Decimal for money with defined rounding. Use a separate semantic-review LLM call only for judgments requiring language understanding, giving it source evidence, applicable instructions, and a strict output contract. A second LLM agreeing with the first is not independent proof of correctness.

For each blank or suspected incorrect field:
1. Check whether it is required/applicable and whether blank is permitted for that record/status.
2. Search all authorized current-case sources and source versions for the value.
3. Locate the original evidence and authoritative source priority. Preserve genuine source conflicts for clarification.
4. Trace raw extraction -> classification -> mapping -> normalization -> family linkage -> eligibility -> source selection -> comparison -> writer -> saved workbook cell.
5. Identify the earliest stage with a provable deviation. Record a short factual cause summary, relevant rule, source location, and observed before/after states. Do not store hidden chain-of-thought.

Diagnoses can include ACCESS_BLOCKED, SOURCE_NOT_PROVIDED, SOURCE_VALUE_ABSENT, PAGE_OR_SHEET_SKIPPED, TEXT_TRUNCATED, ROLE_MISCLASSIFIED, HEADER_MAPPING_FAILED, DEPENDENT_COLUMN_MISSED, LINKAGE_FAILED, INCORRECT_NORMALIZATION, WRONG_SOURCE_VERSION, APPLICABILITY_UNKNOWN, BUSINESS_RULE_MISAPPLIED, CACHE_REPLAY, OUTPUT_SCHEMA_FAILED, WRITER_CELL_MAPPING_FAILED, SBU_TRANSFER_FAILED, or UNDETERMINED. Distinguish confirmed from suspected causes.

If data is genuinely absent, leave it blank and create only an applicable actionable request. If sources conflict, do not choose merely to pass validation. If the cause cannot be verified, retain UNDETERMINED and stop claiming repair success. A learning rule must not be promoted from an unverified diagnosis.

9. CONTROLLED REPAIR AND RERUN LOOP

Implement bounded, transactional remediation; default to one initial attempt plus at most three repair cycles, with configurable time/token/cost limits. Transport retries count toward overall budgets and do not imply a repair succeeded.

Allowed runtime repairs are typed operations implemented by application code, such as:
- re-read a failed page/sheet/table or parse a missing form field;
- re-OCR an affected page using an available engine;
- reclassify a source using evidence or restore an omitted source role;
- apply a validated scoped header/dependent-column mapping;
- repair normalization or subscriber linkage from unambiguous source evidence;
- select the correct supported source version/period;
- replace an incorrect structured value with a source-supported value;
- recompute applicability, matching, summaries, and missing-information findings;
- regenerate a workbook from the approved template or repopulate SBU;
- bypass/evict an affected response-cache entry and re-extract.

Do not evaluate code from learning JSON, run model-generated shell commands, install dependencies, alter business instructions, remove template protection, weaken tests, or modify production Python files during a live prospect run. A true parser/code defect that cannot be handled by an approved strategy becomes a regression fixture and proposed engineering change. During this implementation task, make and test necessary code fixes in the normal development workflow.

Apply repairs to a working snapshot, never original uploads. Require source evidence, compatible scope, validated preconditions, and an expected old-state check. A learned strategy may guide extraction; every resulting current-case value must still be grounded in the current sources. Deterministic business-rule derivations are permitted only where the master explicitly authorizes them and must carry that provenance.

Rerun the earliest changed stage and every downstream dependency from immutable upstream evidence. Invalidate affected results, findings, email bullets, workbook versions, and cache entries. Do not recursively call the public run_pipeline entry point from the Learning Engine. Expose reusable internal stages/checkpoints and maintain one run/attempt controller to avoid nested retries and duplicate files.

After every attempted repair:
- Compare before/after values, failed checks, and record identities.
- Rerun affected validators and the full release-critical checks.
- Require targeted failures to resolve without unexplained row loss/additions, unsupported values, new critical failures, or contradictory findings.
- Roll back a harmful/no-improvement patch and record the actual outcome.
- Stop if evidence is missing, the action signature/state hash repeats, no progress occurs, a repair oscillates, the capability is unavailable, or a budget is exhausted.

Do not rerun unchanged source with the same prompt hoping that repeated agreement proves correctness. New attempts must address the diagnosed failure or produce new evidence. Preserve the best verified candidate, not merely the last output.
